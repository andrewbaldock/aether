# Design tokens

Every table on this page is **derived, not written**. The colour list is parsed
out of `src/index.css` at build time (a Vite `?raw` import — the same
`parseTokens.ts` the in-app `/style-guide` page uses), and the type and font
tables come from the exported records in `useAppearance.tsx`. If a token changes
in the CSS, this page changes with it. There is no copy to keep in sync.

Use the **theme toolbar toggle** above to see any story render against the other
side of these values.

## Colour

Each token resolves through one indirection: `@theme` registers the Tailwind
utility, `:root` and `.dark` hold the values.

```css
@theme { --color-surface: var(--surface); }
:root  { --surface: #ffffff; }
.dark  { --surface: #171717; }
```

Which means `bg-surface` is written once and is correct in both themes forever.

### Reading the families

- **Surfaces** — a four-step elevation ramp: `surface` (the page) → `surface-raised`
  (sidebar, panels) → `elevated` (hover fills, assistant bubbles) → `selected`
  (the active row, deliberately stronger than a hover). `surface-overlay` is the
  odd one out: it stays dark *even in light mode*, because the tooltip bubble
  needs contrast against neon.
- **Content** — four steps of de-emphasis: `content` → `content-muted` →
  `content-subtle` → `content-faint`. Named by role, not by grey value, so the
  dark ramp can invert without a single rename.
- **Accent** — neon pink, the brand. `on-accent` is its paired foreground, which
  is *not* simply white in dark mode: it's a near-black with a pink cast, because
  white on `#ff2e9a` is the kind of contrast failure that only shows up on a real
  screen.
- **Neon / Danger** — the fixed brand pair, and the destructive-action pair used
  by `ConfirmDialog`'s `danger` variant.

## Data-viz ramp

Eight categorical slots for chart series, assigned in sequence. This ramp is the
one place a *number* of colours matters, so it gets its own rules:

- **The order is load-bearing.** It is the colour-blind-safety mechanism, not a
  preference — adjacent pairs are validated for separation under protanopia and
  deuteranopia (OKLab ΔE ≥ 8; worst adjacent pair 9.1 light / 8.4 dark), plus a
  normal-vision floor of ΔE ≥ 15 (19.6 / 19.3). Re-ordering silently voids that.
- **Both modes are selected.** The dark column is the same eight hues re-stepped
  for the near-black surface, not an automatic lightening.
- **The brand pink is deliberately absent.** `--accent` means *you can click
  this*; a pink series would read as an affordance. Identity and action stay on
  separate channels.
- Three light slots (aqua, yellow, magenta) sit under 3:1 on white. That's
  allowed only because the values are legible another way — axis ticks, the hover
  tooltip, and the legend's text labels. Keep that relief if you touch them.

  <VizRamp />
</div>

Unlike every other token here, this ramp is **not** registered in `@theme`.
Tailwind v4 tree-shakes theme entries that no utility class references, so a
`--color-viz-*` declared there resolves to the *empty string* at runtime — charts
render with no stroke and no error. These are consumed as raw values by Recharts
(straight into an SVG `fill`/`stroke`), and a per-series class name would be
dynamic (`bg-viz-${i}`), which Tailwind can't see statically either. So they live
in `:root` / `.dark` as plain themed custom properties: same indirection, same
theme flip, nothing to tree-shake. See **Widgets/Chart palette**.

## Knowledge-graph entity palette

A *second* categorical set, for the five entity types in the knowledge graph.
Separate from the chart ramp because it answers a different question — "what kind
of thing is this node" rather than "which series is this" — and because two of
its slots are load-bearing brand: `person` is the neon pink, `concept` is the
wordmark's mid gradient stop.

The previous values were tuned for the dark canvas and measured badly on the
light one: `place`, `org` and `event` sat at **2.06:1, 2.03:1 and 1.92:1** against
white — visibly washed out. Those three were re-stepped; the two brand ties were
already passing and are untouched.

  <KgPalette />
</div>

**One set serves both themes, and that's a measured result rather than a
shortcut.** Unlike `--viz-*`, requiring each colour to clear 3:1 on white *and*
on the near-black canvas pins it to a narrow mid-lightness band — searching both
surfaces jointly collapsed the feasible region to a single palette. So these are
declared once under `:root` and the dark theme inherits them.

Validated on both surfaces under **all pairs** — the harder test, and the right
one for a force graph where any two nodes can drift adjacent:

| Check | Result |
|---|---|
| Lightness band, chroma, contrast ≥ 3:1 | pass, both surfaces |
| Normal-vision floor (≥ 15) | ΔE 15.4 |
| CVD separation (target ≥ 8) | ΔE 7.0 — `concept`↔`place`, deutan |

That 7.0 is in the **6–8 floor band**, which is legal *only* alongside secondary
encoding. The graph has it: every node renders a lucide icon, a text label, and
an `aria-label`, so colour is never the sole channel. Five hues cannot clear ΔE 8
all-pairs — no ordering of five can — so the labels aren't a nicety here, they're
what makes the palette valid. Keep them.

## Typography

A four-step scale, exposed to the user as a setting rather than hidden as a
constant. Tailwind's `text-*` utilities are rem-based, so changing the root
`font-size` scales the entire app proportionally — one value, no per-component
overrides. `md` is the browser default, so the untouched experience is the
standard one.

The body face is user-selectable too. The brand face (`font-display`, Space
Grotesk) is deliberately *not* — it's the app's voice, not a preference.

## Spacing

One variable, `--spacing: 0.25rem`, declared in the `@theme` block. Tailwind v4
compiles *every* spacing utility against it:

```css
.p-4   { padding: calc(var(--spacing) * 4) }
.gap-2 { gap:     calc(var(--spacing) * 2) }
```

…and the same for margin, width, height, inset, and translate. **The app's whole
rhythm is a single number.** Change it and everything rescales in proportion,
with no component edits — which is the demo: turn one knob, watch the entire
interface breathe in or out.

4px is chosen, not merely inherited — it's the smallest step that divides the
44px minimum touch target evenly (11 steps) and keeps common sizes on whole
pixels. It's declared explicitly even though it matches Tailwind's default,
because an undeclared default is not a decision: without that line nothing
records that the rhythm was ever considered, and nothing tells the next person
where to change it.

Named `--space-1..12` tokens were considered and rejected. They'd sit *beside*
the utilities rather than behind them, so using them would mean migrating every
component to arbitrary values (`p-[var(--space-4)]`) — more code, worse code —
while `p-4` kept routing through `--spacing` regardless. Authoring the variable
the framework already reads is the smaller and more honest change.
