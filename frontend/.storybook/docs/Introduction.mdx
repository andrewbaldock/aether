# Aether's design system

Aether is a conversational explorer: you ask a question, and the answer arrives
as a canvas of widgets — charts, tables, timelines, image grids, a force-directed
knowledge graph — beside the prose. Five widget types, two themes, two shells.

**→ [See it running at aether.andrewbaldock.com](https://aether.andrewbaldock.com)**
&nbsp;·&nbsp; the live app these components are taken from. (The wordmark at the
top-left of this sidebar links there too.)

**→ […and the in-app Style Guide](https://aether.andrewbaldock.com/style-guide)**
&nbsp;·&nbsp; the same system, but *running*: real components on the real page,
with the live theme toggle. This Storybook is the isolated view — one component
at a time, every state, prop tables, accessibility notes. The two are
deliberately separate views of one system, and both read their tokens from the
same parsed `index.css`, so neither can drift from the other.

This Storybook documents the parts that are genuinely *shared*. It is built from
the app's own `vite.config.ts` and imports the app's own `src/index.css`, so
every story renders through the real pipeline against the real tokens. Nothing
here is a re-declaration of the app — it ships **inside the app's own deploy**,
at `/storybook`, from the same build.

## Token architecture

One indirection layer, and only one:

```
@theme            --color-surface: var(--surface)      ← registers the Tailwind utility
:root             --surface: #ffffff                    ← light value
.dark             --surface: #171717                    ← dark value
```

A component writes `bg-surface` and never learns what theme it is in. The utility
class is stable; only the value underneath it flips. That is the whole mechanism —
there is no `isDark` prop, no theme-aware component, and no conditional class
anywhere in the tree.

The practical test: adding a theme means adding a block of values. It should
require zero component changes. See **Foundations/Design Tokens** for the live
token list, parsed out of `index.css` itself.

## Zero-flash boot

Theme, text size, body font, and any Theme-Lab palette overrides are all applied
by an inline script in `index.html` **before first paint**, then kept in sync
after mount by `useTheme` / `useAppearance`. The React state is seeded by the same
resolution logic the pre-paint script uses, so the app never re-flips on mount.

The full loop is: OS preference → explicit user override → `localStorage`
persistence → pre-paint application. Not a toggle bolted onto a stylesheet.

## One motion language

Two animations carry most of the app's character, and they share a mechanism:

- **The skeleton cascade.** Each placeholder card gets a `--i` index custom
  property; the CSS reads it as an animation delay, so planned cards ripple into
  the canvas in order rather than appearing at once.
- **The starter pills.** Same `--i`, same staggered entrance.
- **Table rows.** Same again — clamped in JS to the first ~24 rows so a large
  table doesn't ripple for a second and a half.

Because the delay lives in CSS and the index is just a number the component
hands over, the two read as one system rather than two animations that happen to
coexist. See **Widgets/SkeletonCard** and **Shell/StarterPrompts**.

## Two shells

The system has exactly two composed shells, and between them they own all the
chrome in the app.

**`CardShell`** is the single wrapper every card on the Bigsail canvas renders
through. It owns the drag strip, title, action cluster, skeleton entrance, and
the 3D flip that reveals a widget's JSON spec. The component inside it is a
dispatcher that renders only type-specific *content* — so a new widget type
implements its content and inherits its entire chrome, and the flip (notoriously
fiddly in a `preserve-3d` scene) is implemented exactly once. See
**Widgets/CardShell**, which shows all five capabilities in the same shell.

**`AdminPage`** does the same job for the utility pages — Welcome, Settings,
Health, Metrics, Style Guide, Theme Lab. Before it existed, each page rolled its
own scroll container, width, padding, tab slot, and heading size, so *navigating
between them made the column jump*. Each page looked fine alone; the system only
failed in the transition. See **Shell/AdminPage**.

## Composition over configuration

The shell primitives take *elements*, not config. `ConfirmDialog` takes a
`trigger` and wraps whatever button it guards. `Tooltip` and Radix's `asChild`
merge behaviour onto the caller's own element, so layout classes passed from a
call site keep working untouched.

Consequently the variant APIs stay small on purpose: `ConfirmDialog` has exactly
two (`primary` for reversible, `danger` for destructive). A third would only
invite guessing.

## Schema heal-on-load

Widget specs are versioned. On load, a spec whose `schemaVersion` doesn't match
is cleared rather than migrated — the answer is regenerable, so healing beats
maintaining a migration ladder for a demo's worth of persisted state. Honest
about its own trade-off: this is a policy that works *because* the data is cheap
to recreate.

## What isn't here yet

Kept explicit so the docs stay trustworthy:

- **`AdminTabs` is not a compound component.** It's a `.map()` over a tab array,
  and it's coupled to the router, which is why it has no story yet.
- **No visual-regression suite.** The a11y addon runs axe per story; there is no
  snapshot diffing.
